
## Problem

SAP Commerce (Hybris) business processes описываются в XML и реализуются через Java action-классы. На крупных проектах процессы разрастаются до десятков узлов с глубокими ветвлениями. Даже визуализация через SAP Commerce Plugin в IntelliJ IDEA не даёт понимания **логики переходов** — диаграмма показывает граф, но не объясняет *при каких условиях* процесс идёт в ту или иную ветку.

**Результат:** понять как работает процесс можно только вручную читая цепочку Java-классов — это занимает часы и требует держать весь граф в голове.

---

## Current Behavior

- Разработчик открывает XML процесса (например `order-process.xml`)
- Видит узлы: `<action id="checkPayment" bean="CheckPaymentAction">`, transitions: `OK → nextStep`, `NOK → errorStep`
- Чтобы понять что делает `CheckPaymentAction` — идёт в Java, читает `executeAction()`, смотрит что возвращает
- Повторяет для каждого узла в цепочке
- Итог: 20+ классов, логика в голове, высокий риск упустить ветку

---

## Desired Behavior

Запустить инструмент, указать путь к XML процесса — получить:

1. **Читаемый отчёт** — для каждого action: что делает, при каких условиях какой transition возвращает и почему
2. **Mermaid-диаграмму** — с подписями на переходах (не просто `OK/NOK`, а `"payment confirmed"` / `"payment failed"`)

---

## Constraints

- Код проекта не должен покидать локальную машину — никаких загрузок в облако
- Инструмент должен работать автономно: на входе XML, на выходе отчёт
- ИИ агент уже установлен локально (Claude Code / Codex)
- Решение не встраивается в проект — это dev-утилита

---

## Possible Solutions

### Вариант 1 — Claude Code Skill

Написать кастомный скилл для Claude Code:

- **Вход:** путь к XML процесса + путь к корню проекта
- **Шаг 1:** парсинг XML → извлечение всех `<action>` узлов, их `bean`-имён и `<transition>` маппингов
- **Шаг 2:** поиск Java-файлов по имени бина (glob по проекту)
- **Шаг 3:** чтение `executeAction()` каждого класса + зависимостей
- **Шаг 4:** Claude анализирует код каждого action и описывает логику переходов
- **Шаг 5:** генерация отчёта в Markdown + Mermaid блок

**Плюсы:** нативная интеграция с Claude Code, умеет сам читать файлы, не нужен отдельный скрипт
**Минусы:** требует написания `.md` скилла с чёткими инструкциями

---

### Вариант 2 — Python скрипт + Claude API

Standalone скрипт:

```
python analyze_bpm.py --xml path/to/process.xml --src path/to/src/main/java
```

- `xml.etree` парсит XML процесса
- `pathlib` ищет Java-файлы по имени бина
- Каждый action отправляется в Claude API (`claude-sonnet`) с промптом
- Результат собирается в единый `report.md`

**Плюсы:** просто, переносимо, легко дорабатывать
**Минусы:** требует API ключ, нужен Python окружение

---


## How We Verify Success

- [ ] На вход подан реальный XML процесса (`order-process.xml` или аналог)
- [ ] Отчёт содержит описание каждого action — что делает и какие transitions возвращает при каких условиях
- [ ] Mermaid-диаграмма рендерится корректно и подписи на переходах отражают бизнес-логику (не просто `OK/NOK`)
- [ ] Код проекта не покидает локальную машину
